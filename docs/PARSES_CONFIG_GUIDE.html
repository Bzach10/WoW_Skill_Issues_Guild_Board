The Parses Pipeline

How per-character Warcraft Logs data reaches the website — and every knob you can turn, in one page.

This guide covers the per-character parse pipeline added 2026-07-24: what runs where, which files you may edit, and exact steps for the changes you're most likely to want. For board cosmetics see theme.yml + CUSTOMIZING.md; for the front-end data shapes see WEB_DATA_CONTRACT.md (section 7, "parses").

1The pipeline at a glance

1
WCL Parse Refresh CI only · daily 13:30 UTC .github/workflows/wcl-parse-refresh.yml runs scripts/refresh_parses.py with the WCL_CLIENT_ID/WCL_CLIENT_SECRET repo secrets. Sweeps every roster member's current-tier rankings (mythic → heroic → normal, first hit wins). On your PC the same script prints a note and exits — no credentials exist locally, on purpose.
▼
2
parses_cache.json CI-owned — never hand-edit RAW truth: each character's best-performance average, per-role averages, difficulty, tier, timestamp — keyed name-realm (exact Unicode, e.g. violënce-bleeding-hollow). Fail-open: a bad WCL day keeps yesterday's cache instead of blanking the site.
▼
3
Bundle build runs anywhere scripts/build_site_data.py reads the cache plus your scale factors from config.yml and emits parses.json + merges each character's parse into competition.json. Scaling happens HERE, at build time — retuning a factor never requires re-pulling Warcraft Logs.
▼
4
Validate, then deliver — all or nothing scripts/validate_bundle.py refuses any bundle whose layers disagree; scripts/deliver_bundle.py hands the complete 7-file set to C:\dev\wipefest-redesign\data\source with a DELIVERY.json receipt. No step ever copies one file by hand — that caused the 2026-07-23 split-brain.
▼
5
The website Four Emperors ranking (Emperor Index = equal blend of M+ score/top-score and scaled parse-avg/100), standings parse columns, newspaper raid sections.

2The knob you'll touch most: difficulty scale factors

A heroic 95 shouldn't outrank a mythic 80 on the Emperor Index. Each character's average is multiplied by the factor for the difficulty their logs come from. In config.yml:

# config.yml — safe to edit right on GitHub (pencil icon), then commit.
parses:
  difficulty_scale:
    mythic: 1.0   # full credit
    heroic: 0.8   # heroic averages count 80%
    normal: 0.0   # 0 = EXCLUDED — normal parses don't appear at all
👑
Mythic raider
80.0
× 1.0
= 80.0
 
Heroic raider
95.0
× 0.8
= 76.0
 
Normal raider
95.0
× 0.0
not listed
0 means "not available", not "0%". A difficulty scaled to 0 is excluded end-to-end: its characters drop out of the parses layer (the site shows its normal "no logs yet" state — never an embarrassing 0.0% row) and the refresh Action skips querying that difficulty, saving API budget. The raw numbers stay in the cache, so flipping normal back to, say, 0.5 later restores everyone on the next rebuild — nothing is lost.

Every character keeps both numbers: best_perf_avg (raw — show this on cards, labeled with the difficulty) and scaled_perf_avg (discounted — rankings use this). The bundle also records which factors were applied, so an old bundle can't lie about its tuning.

When does a change take effect? On the next bundle rebuild — the 13:30 UTC parse Action, the 14:00 UTC competition Action, or a manual run (recipes below). No Warcraft Logs re-pull needed; the cache stays raw.
Guardrails already built in: factors are forgiving (a typo like heroic: banana falls back to 1.0; negatives clamp to 0, which counts as excluded), and scaled values cap at 100 even if you set mythic above 1.0.

3Recipes — "how do I…"

…soften or harden the heroic discount?
  1. Edit config.yml → parses.difficulty_scale.heroic (e.g. 0.9 softer, 0.7 harder)
  2. Commit to main
  3. Wait for the next scheduled Action, or trigger one (next recipe)
…bring normal parses back, or go mythic-only?
  1. Back on: set normal: to any factor > 0 (e.g. 0.5) — everyone reappears on the next rebuild, nothing was lost
  2. Mythic-only: set heroic: 0.0 too
…apply a config change right now?
  1. GitHub → Actions → WCL Parse Refresh → Run workflow
  2. It refreshes, rebuilds, validates, commits — done in a few minutes
…run the cycle on my PC?
  1. python scripts/build_site_data.py
  2. python scripts/validate_bundle.py web_data
  3. python scripts/deliver_bundle.py --from web_data
  4. (refresh_parses.py is a no-op locally — data comes from the committed cache)
…change how often parses refresh?
  1. Edit the cron: line in .github/workflows/wcl-parse-refresh.yml
  2. Currently 30 13 * * * = daily 13:30 UTC; 30 13 * * 3,6 = Wed + Sat only
…pin the raid tier manually?
  1. config.yml → rankings.zone_id (0 = auto-detect from recent logs)
  2. Set the WCL zone id to force a specific tier (useful at season boundaries)
…adjust the "bad WCL day" safety net?
  1. The refresh keeps the old cache if a sweep resolves < 50% of last run's characters
  2. Change it: add --min-fraction 0.3 to the refresh step in the workflow
…rotate the WCL credentials?
  1. warcraftlogs.com → your client at /api/clients → regenerate secret
  2. GitHub → Settings → Secrets and variables → Actions → update WCL_CLIENT_ID / WCL_CLIENT_SECRET
  3. Secrets never exist locally, and no output file ever contains them (a test enforces this)
…check why someone shows "no logs yet"?
  1. They're absent from parses_cache.json = WCL has no ranked kills for them this tier at any difficulty
  2. They must appear in uploaded logs — check their page on warcraftlogs.com

5The laws of this pipeline

Keys are always name-realm, exact Unicode. Two characters can share a name across realms (violënce-bleeding-hollow ≠ violënce-area-52). Bare-name keying already destroyed data once (board_state's season_scores); every parse structure keys the full pair, and tests enforce it.
The bundle ships whole or not at all. The validator refuses mixed builds; the deliverer copies the complete 7-file set or nothing. Never hand-copy one JSON into the redesign repo.
Raw is sacred; scaling is presentation. Scale factors are applied at build time and recorded in the output. The cache always holds the untouched WCL numbers, so any future re-tuning is loss-free.
Local = credential-free. Anything needing WCL/Blizzard/Discord secrets runs only in Actions. Local scripts are inert or degrade gracefully — if something demands a credential on your PC, that's a bug.
